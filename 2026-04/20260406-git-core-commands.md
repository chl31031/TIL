# 📜 Git 핵심 명령어 가이드

### 1. 로컬 저장소 관리 (Local Workflow)
프로젝트의 시작과 변경 사항 기록에 관한 명령어입니다.

* **`git init`**: 현재 디렉토리를 Git 저장소로 초기화합니다. `.git` 폴더가 생성되며 버전 관리가 시작됩니다.
* **`git status`**: 현재 작업 디렉토리와 스테이징 영역(Staging Area)의 상태를 확인합니다. (수정된 파일, 추적되지 않는 파일 등)
* **`git add <파일명>`**: 변경 사항을 스테이징 영역에 추가합니다. `git add .`을 사용하면 모든 변경 사항을 한 번에 담을 수 있습니다.
* **`git commit -m "메시지"`**: 스테이징 영역에 담긴 파일들을 의미 있는 작업 단위로 기록합니다.
    > **💡 Tip:** 메시지 컨벤션(예: `feat:`, `fix:`, `docs:`)을 지키면 히스토리 파악이 훨씬 쉬워집니다.
* **`git log`**: 지금까지의 커밋 히스토리를 조회합니다. (`--oneline` 옵션으로 간결하게 볼 수 있습니다.)

---

### 2. 브랜치 및 병합 (Branching & Merging)
기능별 독립적인 개발을 위한 핵심 기능입니다.

* **`git branch`**: 로컬 브랜치의 목록을 확인하거나 새 브랜치를 생성합니다.
* **`git switch <이름>`**: 다른 브랜치로 이동합니다.
* **`git switch -c <이름>`**: 새 브랜치를 생성함과 동시에 해당 브랜치로 즉시 이동합니다. (기존 `checkout -b`와 동일)
* **`git merge <대상>`**: 현재 브랜치에 다른 브랜치의 작업 내용을 합칩니다.
    > **⚠️ Conflict:** 같은 파일의 같은 부분을 수정했을 때 발생합니다. 충돌 부분을 직접 수정 후 다시 `add`, `commit`해야 합니다.

---

### 3. 히스토리 되돌리기 (Undo Changes)
실수를 바로잡는 고급 기술입니다.

* **`git reset`**: 특정 시점으로 히스토리를 되돌립니다. `--hard` 옵션 사용 시 이후의 기록이 삭제되므로 주의가 필요합니다.
* **`git revert`**: 기존 기록은 그대로 남겨둔 채, 특정 커밋의 내용을 취소하는 '반대되는 커밋'을 새로 추가합니다. 협업 시 기록 파괴를 막기 위해 권장됩니다.

#### 💡 Revert가 Reset보다 안전한 이유
1. **히스토리 보존**: `reset`은 기록을 아예 삭제하지만, `revert`는 "실수를 취소했다"는 기록 자체를 남깁니다. (누가, 왜 취소했는지 알 수 있음)
2. **협업 충돌 방지**: 이미 원격 저장소(`GitHub`)에 올라간 커밋을 `reset`으로 지우고 `push`하면 다른 팀원들의 로컬 저장소와 히스토리가 꼬여 큰 혼란이 생깁니다. `revert`는 새로운 커밋을 추가하는 방식이라 협업 시 안전하게 동기화됩니다.

### 4. 원격 협업 (Remote Collaboration)
팀 프로젝트 및 오픈소스 기여의 핵심 프로세스입니다.

* **`git remote add origin <URL>`**: 내 로컬 저장소와 GitHub 등의 원격 저장소를 연결합니다.
* **`git push origin <브랜치명>`**: 로컬의 커밋 내역을 원격 저장소로 업로드합니다.
* **`git pull origin <브랜치명>`**: 원격 저장소의 최신 변경 사항을 가져와 현재 로컬 브랜치에 합칩니다.
* **`Fork & Pull Request (PR)`**:
    1.  **Fork:** 타인의 저장소를 내 계정으로 복제합니다.
    2.  **Clone:** 내 계정의 저장소를 내 컴퓨터(M2 Mac)로 내려받습니다.
    3.  **Push:** 내 브랜치에서 작업 후 내 원격 저장소에 올립니다.
    4.  **PR:** 원본 저장소 관리자에게 내 수정 사항을 반영해달라고 공식적으로 요청합니다.

#### 🎯 PR을 위한 커밋 단위 (Commit Strategy)
PR을 보낼 때는 **"리뷰어가 읽기 편한 단위"**로 커밋하는 것이 중요합니다.
1. **원자적 커밋 (Atomic Commit)**: 하나의 커밋에는 하나의 기능 변화만 담습니다. (예: 오타 수정과 기능 구현을 한 커밋에 섞지 않기)
2. **논리적 단위**: 기능 하나가 완성되었을 때 커밋합니다. 너무 자잘한 커밋(예: "오타 수정1", "오타 수정2")은 나중에 `squash`하거나 의미 있게 합쳐서 PR을 보내는 것이 좋습니다.
3. **작동하는 코드**: 커밋 단위는 항상 빌드가 성공하고 실행 가능한 상태여야 합니다.
