#### [학습 내용]

- 주제 : 한국주식 모의 투자 앱, Candle

</br>

- 핵심 기능
  1. **회원가입과 로그인 기능**
  2. **실시간 주식 시세 조회 기능**
  3. **모의투자 계좌 생성과 가상 자산 지급 기능**
  4. **주식 매수 및 매도 거래 기능**
  5. **보유 종목 및 자산 현황 조회 기능**
  6. **투자 수익률 및 거래 내역 분석 기능**
  7. **투자 랭킹 시스템**
  8. **투자 미션 및 챌린지 기능**
  9. **투자 학습 콘텐츠 제공 기능**
  10. **마이페이지에서 투자 성과를 관리하는 기능**

</br></br>

- 아키텍처 개요
  - Candle은 실시간 시세 조회, 거래 처리, 랭킹 집계, 미션 처리, 알림 발송 등 기능의 성격이 서로 다르기 때문에 단일 서버로 모든 기능을 처리하기보다는 **MSA 기반 구조**로 설계함

  - 전체 흐름은 크게 다섯 영역으로 나눌 수 있습니다.
  1. **Client 영역** : 사용자는 Web 또는 App을 통해 서비스에 접근합니다.

  2. **AWS Edge 영역** : CloudFront와 WAF를 통해 정적 리소스 제공, 보안 필터링, 기본적인 공격 방어를 수행합니다. 이후 요청은 ALB를 거쳐 API Gateway로 전달됩니다.

  3. **EKS Cluster 영역** : 실제 백엔드 서비스들은 EKS 내부의 Private Subnet에서 실행됩니다. 서비스들은 Auth, Market Data, Account, Trading, Ranking, Mission, Learning, Notification 등으로 분리되어 있습니다.

  4. **Data Layer 영역** : 서비스별 성격에 따라 PostgreSQL 과 Redis를 사용합니다. 영속성이 필요한 회원, 계좌, 거래, 학습 데이터는 Aurora MySQL에 저장하고, 빠른 조회가 필요한 시세 캐시와 랭킹 데이터는 Redis를 사용합니다.

  5. **External 영역** : 카카오 OAuth, 네이버 OAuth, 증권사 API, AWS SES, FCM 같은 외부 시스템과 연동합니다.

</br></br></br>

- BFF Layer
  - Candle은 BFF Layer를 별도로 두었음

  - BFF는 Backend For Frontend의 약자로, 프론트엔드 화면에 필요한 데이터를 여러 서비스에서 조합해서 내려주는 역할을 함.

  - 예를 들어 마이페이지 화면을 생각해보면, 한 화면에 계좌 정보, 보유 종목, 수익률, 랭킹 정보가 함께 필요할 수 있음. 이때 프론트엔드가 Account Service, Trading Service, Ranking Service를 각각 직접 호출하면 클라이언트의 요청 수가 많아지고 화면 구성 로직이 복잡해짐.

  - 그래서 Candle에서는 BFF가 Account, Trading, Ranking 서비스를 병렬로 호출하고, 응답을 조합해서 프론트엔드에 한 번에 내려주는 구조로 설계했음.

  - 이 방식은 화면 단위 응답 최적화에 유리하고, 프론트엔드와 내부 마이크로서비스 구조 사이의 결합도를 낮출 수 있음.

#### [느낀 내용]

- MSA 프로젝트를 처음 해보는데, 주문/결제/계좌 쪽을 맡게 되었다. 다른 서비스에 FK를 두지 않는 독립적인 서비스를 구축해보는 게 처음이라 기대되기도 하고, 잘 할 수 있을지 우려되기도 한다.
